# ADR-0001：为什么提交仿真必须异步

- 日期：2026-10-21
- 状态：已接受
- 相关：`app/services/simulation_service.py`、`app/api/v1/simulations.py`

## 背景

一次运力仿真要模拟几十台车、几百分钟、上万次循环，是**CPU 密集的长任务**。用户在页面上点"开始仿真"，不可能让 HTTP 请求一直挂着等到算完。

同步方案会遇到三个硬伤：
1. 网关/浏览器超时（常见 60s），仿真一旦变慢就直接失败；
2. 请求线程被占满，其他用户连 `health` 都打不通；
3. 页面卡死，用户无法取消。

## 决策

1. `POST /simulations` **立即返回 202 + taskId**，绝不等待计算完成；
2. 计算交给 `ProcessPoolExecutor`（**进程池不是线程池**，仿真是 CPU 密集，Python 有 GIL，线程池等于串行）；
3. 任务状态存 `TaskStore`，状态机 `PENDING → RUNNING → SUCCEEDED / FAILED`；
4. 前端轮询 `GET /simulations/{id}` 获取状态与结果（阶段 5 换成 WebSocket 推送进度）。

## 关键实现约束

- **子进程改不了主进程的内存**：worker 里更新 `TaskStore` 主进程看不到，必须用 `future.add_done_callback()`，回调运行在主进程，才能把 KPI 写回任务表。
- **进程池必须惰性创建**：Windows 用 spawn，子进程会重新 import 主模块；若在模块导入时建池，子进程里再建池会触发 `daemonic processes are not allowed to have children`。
- **worker 函数必须可 pickle**：只能传模块级函数（本项目是 `run_scenario`），不能是 lambda 或对象方法。
- **TaskStore 需要加锁**：提交（主线程）与回调（线程池线程）会并发写。

## 代价

- 任务表在内存，进程重启后任务丢失 —— 阶段 3 换成 SQLite，因已封装成 `TaskStore`，只需替换实现；
- 轮询有延迟（最坏 1s），阶段 5 用 WebSocket 解决。

## 备选方案（未采用）

- **FastAPI `BackgroundTasks`**：跑在同一进程，CPU 密集会阻塞事件循环，等于没解决；
- **Celery + Redis**：能力更强，但 MVP 阶段多两个中间件，运维成本不划算。
